# ITBIS rate list from the database (feature `itbis-tasas-config`)

Branch `feature/itbis-tasas-config`. Replaces the hardcoded `0/16/18` rate sets with a per-empresa list stored in
`CONFIGURACION_EMPRESA` (AGENTS.md: "Parameters from DB, never hardcoded: ITBIS rate (with validity)").
Audit evidence: Log L2. Delivered in slices; each slice ships and is verified on its own.

## Specs

- S1 Direction (owner answer, verbatim): "Yes, in safe slices (recommended)". The allowed ITBIS rate list moves to the database in slices: first remove the duplicated hardcoded copies with ZERO behavior change; then a data migration (the owner applies it); then the application reads the list from the database.
- S2 Rates allowed from day one (owner answer, verbatim): "Keep exactly 18, 16 and 0 (recommended)". Same as today. No new rate is added. Any future rate needs the owner's confirmation that it is legally valid.
- S3 Editing (owner answer, verbatim): "Later, as its own slice (recommended)". First ship the database-driven read with the seeded list. A rate change then goes through a reviewed migration. An Administrador edit screen (audited, optimistic lock) is a LATER slice, built only when the owner asks. It is NOT part of this feature.
- S4 Retired rate (owner answer, verbatim): "Keep history readable, block only new use (recommended)". Old products and old sales keep showing and can be returned (their rate is frozen on the line). Only new sales, purchases and products with that rate are refused. Reads never crash.
- S5 Storage: reuse `CONFIGURACION_EMPRESA` (key, value, `vigenciaInicio`/`vigenciaFin`, `activa`, `version`). One key `TASA_ITBIS` per empresa, `valor` a comma list such as `18,16,0`. No new table, no CHECK constraint. Seeded identically for every empresa by an idempotent data migration (`ON CONFLICT DO NOTHING`), like `RETROACTIVO_FECHA_VENTA_DIAS`.
- S6 Domain stays pure: validators take the allowed rates as a parameter; the application layer reads the key with `leerConfigActivaEnTx` inside `withTenantTransaction` and passes it down. A missing key fails loud with a stable error code (like `CONFIG_RETENCION_FALTANTE`), never a silent default.
- S7 Snapshots do not change: `tasaItbis` stays frozen per line (`VENTA_DETALLE`, `DEVOLUCION_DETALLE`, `COMPRA_DETALLE`). Only the list of rates allowed for NEW use is dynamic. A return validates the frozen line rate, not the current list.
- S8 Money rule: rates are `Decimal` / decimal strings, never `number`. Precision stays `Decimal(12,2)`.
- S9 Slice 1 changes NO behavior: same accepted set `{0,16,18}`, same error codes, same UI options and labels, same messages (the error text may be derived from the constant but must render the same sentence for the same set).
- S10 Tests: domain unit with no database; every touched command keeps a test proving its previous behavior; integration against real Postgres (`systemfact_app`) for the config read and for the empresa isolation; e2e for product create/edit with each of the three rates. No test may skip.
- S11 Each shipped slice carries its own version bump (`app/package.json`, `.release-please-manifest.json`, `app/CHANGELOG.md`, UTF-8 without BOM), Conventional Commits, a migration in its OWN commit, owner-approved merge and deploy, production smoke, and the production demo lane after a deploy that touches sales, returns or login.
