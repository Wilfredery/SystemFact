# Administración writes (Step 7b) — role assignment and activate/deactivate, RLS-enforced

Branch `feature/administracion-writes` · target v0.28.0 · issue-first PR gate. Owner delegated the RLS and scope choices to the agent ("do whats the professional best practical, safe and security way").

## Specs

- S1 Scope of THIS PR (agent decision under owner delegation, L2): only two writes on EXISTING users of the session branch: (a) set a user's roles, (b) activate/deactivate a user. NO user creation, NO password/Auth-user handling, NO service-role key anywhere in the app runtime (owner decision `odd/tasks/security-hardening.md` L13, `app/USER-PROVISIONING.md`). NO branch moves and NO branch create/edit, NO company-wide user listing (deferred to a later PR together with the RLS widening it needs).
- S2 RLS is role-aware, in its OWN migration commit (AGENTS.md Git workflow): writes (INSERT/UPDATE/DELETE) on `USUARIO` and `USUARIO_ROL` require `app.current_es_admin = 'true'` plus the existing tenant/branch scope; SELECT policies are NOT widened. The existing exceptions stay exactly as they are and nothing else loosens: `app.is_bootstrap` (seed/provisioning) and the login flow (`app.is_login_flow`: the lazy `authUserId` bind and Auth lookup MUST keep working). `ROL` writes stay bootstrap-only. Audit stays append-only.
- S3 Server-side authorization on every write: the action checks the DB role through the existing `tieneRolPermitidoEnTx` with a named group in `tenant/http/shared.ts` (e.g. `ROLES_GESTION_USUARIOS`, Administrador), deny-by-default, `TEN_OPS_NO_AUTORIZADO` on denial. The role name is written in that ONE place only. RLS is the second, independent wall (S2): a test must prove that an Operador/Despachador session is refused by the DATABASE itself even when the app guard is bypassed.
- S4 Roles use SET semantics: `cambiarRolesUsuario(usuarioId, rolIds[], versionEsperada)` replaces the user's role set with a non-empty list of active ROL ids from the catalog (unknown/inactive/duplicate id → typed business error). Idempotent: repeating the same call changes nothing and writes no second audit row.
- S5 `cambiarEstadoUsuario(usuarioId, activo, versionEsperada)` only flips `activo` (never DELETE; users are master entities, AGENTS.md). Idempotent the same way.
- S6 Optimistic locking: both writes require the `Usuario.version` the screen read and increment it; a stale version returns a typed conflict (stable code) and changes nothing.
- S7 Safety invariants, enforced INSIDE the transaction (row locks, never check-then-write outside it): (a) a user cannot deactivate themselves or remove their own Administrador role; (b) the branch can never be left without at least one ACTIVE Administrador (count under the same lock; counts only what RLS shows, which can only err toward refusing, documented); (c) the target must belong to the caller's `empresaId` (and branch, by RLS) — a foreign id behaves as not found, never as a leak.
- S8 Every successful write appends ONE audit row (who, target user, before/after roles or estado) through the project's existing audit mechanism; no UPDATE/DELETE on audit. A refused or no-op call writes none.
- S9 Deactivation is effective on the next request: the per-request identity path already rejects `activo=false`; an integration test pins that `getCurrentTenantContext` returns null for a user deactivated by this action (no signOut/service-role needed).
- S10 Typed results with stable codes added to the tenant error catalog only (no ad-hoc codes in adapters/components); no Prisma in `http/`; all DB access in `withTenantTransaction`; no stack traces or Prisma errors to the client.
- S11 UI (Administrador only, server-gated like the existing tab): an `Acciones` column on Usuarios with "Cambiar roles" and "Desactivar/Activar", dialogs with explicit confirmation, buttons disabled while pending, server confirmation before showing the new state (no optimistic fiscal-style UI), stable-code messages in Spanish. Operador/Despachador keep the access message with no controls and no `Acciones` column. The "no write affordance" assertions of `e2e/administracion.spec.ts` are replaced by the exact new contract.
- S12 Tests: domain unit (invariants, no DB); use-case unit; integration against real Postgres as `systemfact_app` with Administrador and Operador sessions (S2/S3 DB wall, S7 incl. a concurrency test on last-admin, S8, S9); RTL for the dialogs/column; e2e for the Administrador flow and the Operador/Despachador no-controls contract. Every existing integration suite stays green (login flow untouched). No test may skip.
- S13 Version bump 0.28.0 (feat → MINOR): `app/package.json` + `.release-please-manifest.json` + `app/CHANGELOG.md` in the final patch commit, UTF-8 without BOM; squash-merge with `Closes #N`; production deploy only with the owner's explicit approval (this PR touches login/RLS: run the production demo lane after deploy per the standing order).
