# Administración — move a user to another branch (slice A of "branch moves + branch management")

Branch `feature/administracion-mover-usuario` · target v0.32.0 · no migration, no RLS change. Slices B (branch create/rename) and C (branch activate/deactivate) stay OPEN: both need a `SUCURSAL` RLS migration the owner applies.

## Specs

- S1 Scope of THIS PR: ONE write, "move one existing user to another active branch of the same company": `moverUsuarioDeSucursal(usuarioId, sucursalDestinoId, versionEsperada)`. Administrador only (docs/04-rolesPermisosFact.md:224-226: "The Administrator is also the only one authorized to MOVE PERSONNEL (assign users) to different branches."). NO branch create/rename/deactivate, NO user creation, NO change to any migration or RLS policy, NO change to `SUCURSAL`.
- S2 Server-side authorization: the action checks the DB role with the existing `tieneRolPermitidoEnTx` and the existing group `ROLES_GESTION_USUARIOS` (`tenant/http/shared.ts:41`), deny-by-default, `TEN_OPS_NO_AUTORIZADO` otherwise. All DB access inside `withTenantTransaction`. Typed results with stable codes in the tenant error catalog only (`tenant/domain/errors.ts`); no Prisma in `http/`; no stack/Prisma error to the client.
- S3 Target validation INSIDE the transaction: the destination must be a branch of the SAME empresa with `activa = true` (reuse the existing active-branch lookup, `repo-sucursal.ts`); the target user must belong to the session empresa (any of its branches; read under the company-wide widen). Unknown/other-empresa/inactive destination or unknown user → typed business error, nothing written.
- S4 Safeguards, owner decision L2 ("No, refuse it"): (a) a user can NOT move themselves (use the existing branch switch instead): reuse `TEN_AUTO_PROTECCION`; (b) a move that would leave the SOURCE branch without an ACTIVE Administrador is refused with the existing `TEN_ULTIMO_ADMINISTRADOR`. The count is of the SOURCE branch explicitly (the existing rule counts "the branch as seen under RLS", which is the wrong branch here). Decided in the pure domain (`domain/usuario-gestion.ts`), testable without a database.
- S5 Concurrency and idempotency: row locks inside the transaction on the target user AND the active Administradores of the source branch AND of the destination branch, in ascending id order (reuse/extend `bloquearUsuarioYAdministradoresEnTx`); optimistic lock on `Usuario.version` (stale → the existing `TEN_CONCURRENCIA_CONFLICTO`, nothing changed); the write is a verified `UPDATE ... WHERE id AND empresaId AND version`. Moving to the branch the user already has is an idempotent no-op: success, no version bump, NO audit row.
- S6 RLS mechanism (verified in the audit, no migration): `usuario_update` USING and WITH CHECK require `es_admin = 'true'` + same empresa + (branch GUC blank OR sucursalId = GUC). The lock, the count and the single UPDATE therefore run with the branch GUC blank (the existing widen pattern `conSucursalAmpliadaEnTx` / `liberarSucursalActivaEnTx` in `repo-sucursal.ts`), the empresa GUC is NEVER touched, the GUC is restored in `finally`, and the audit insert and everything after run with the session branch pinned again. The widen must never wrap more than those statements.
- S7 Audit: a successful move appends ONE audit row (actor, target user, branch before and after) through the existing `registrarAuditUsuarioEnTx`; append-only; a refused or no-op call writes none.
- S8 Effective on the next request: `getCurrentTenantContext` re-reads the user on every call, so a logged-in moved user is on the new branch on their next request. An integration test pins it (the moved user's context reports the destination branch right after the move).
- S9 History stays where it was made: documents (ventas, facturas, pagos, compras, movimientos) keep their own `sucursalId`; nothing but `USUARIO.sucursalId` (+ `version`, `updatedAt` if the schema has it) changes. BORRADOR documents are not moved.
- S10 UI (Administrador only, same server gate as the tab): a **"Mover de sucursal"** action in the `Acciones` column of Usuarios, available on rows of ANY branch except the session user's own row (disabled with the existing own-user title). It opens a dialog with a select of the company's ACTIVE branches excluding the user's current one (data from the existing branch list use case), explicit confirmation, button disabled while pending, definitive state shown only after the server confirms (fiscal-style "never optimistic"), typed error messages from the code catalog. The existing role and activate/deactivate buttons of other-branch rows stay disabled exactly as in v0.31.x (their writes are still pinned to the session branch).
- S11 Tests: domain unit (self-move, last admin of the SOURCE branch, same-branch no-op, no database); use-case unit; integration against real Postgres as `systemfact_app` with Administrador and Operador sessions: Operador refused at the action gate AND at the database (RLS wall: an Operador UPDATE of `USUARIO.sucursalId` under a blank GUC changes 0 rows), admin move works across branches, destination of another empresa refused, inactive destination refused, last-admin refused, self-move refused, stale version refused, same-branch no-op writes no audit and no version bump, audit row written once, GUC restored after the move (a later write in the same transaction is pinned again), moved user's next context shows the new branch, concurrency test on the last admin (two parallel moves of the two admins of a branch: at most one succeeds). RTL for the action, the dialog and the disabled own row. e2e: the Administrador moves a throwaway fixture user to the other branch and sees it in the list; it must not skip (`app/e2e/assert-no-skips.mjs`).
- S12 Version bump 0.32.0 (feat → MINOR) in `app/package.json` + `.release-please-manifest.json` + `app/CHANGELOG.md` (UTF-8 without BOM) in the final patch commit; native review (risk + resilience lenses) before the push; production deploy only with the owner's explicit approval. No production migration, so the owner has nothing to apply.
