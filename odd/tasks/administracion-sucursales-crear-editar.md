# Administración — create and edit branches (slice B of "branch moves + branch management")

Branch `feature/administracion-sucursales` · target v0.33.0 · ONE policy migration (owner applies it to production BEFORE the deploy). Slice A (move a user, v0.32.0) is shipped. Slice C (activate/deactivate a branch) stays OPEN.

## Specs

- S1 Scope of THIS PR: two writes on `SUCURSAL`, Administrador only: (a) **create a branch** (`nombre`, `direccion`, `telefono`), (b) **edit a branch** (the same three fields). NO activate/deactivate (slice C), NO delete (branches are master entities with history, never deleted; every document table references `sucursalId` with Restrict), NO inventory setup (stock rows are created lazily, a new branch needs nothing), NO change to the user move.
- S2 Database wall, in its OWN migration commit (AGENTS.md Git workflow), `20261115120000_sucursal_writes_admin_only`, model = `20261114120000_usuario_writes_admin_only` (WHY/WHAT/IDEMPOTENT/ROLLBACK header): replace the single `FOR ALL` policy `sucursal_isolation` by `sucursal_select` (EXACTLY the old USING, no read widened), `sucursal_insert` and `sucursal_update` (USING and WITH CHECK: `app.current_es_admin = 'true'` AND `empresaId = app.current_empresa_id`, OR `app.is_bootstrap = 'true'`), and `sucursal_delete` (bootstrap only: nobody deletes a branch through the application). No GRANT change (the app role already has the privileges; RLS is the only wall). FORCE RLS stays. Same migration: `ADD COLUMN "version" INTEGER NOT NULL DEFAULT 1` on `SUCURSAL` (house rule: every master edited concurrently has a `version`, Directiva §10) and a functional UNIQUE index `(empresaId, lower(btrim(nombre)))` written as raw SQL (Prisma cannot express it; add a comment in `schema.prisma` next to the model). Production was checked on 2026-11-14 (read-only, Supabase MCP): 1 empresa, 1 branch, ZERO duplicate names, so the index can be created. `prisma/schema.prisma` gets `version Int @default(1)` on `Sucursal`.
- S3 Server-side authorization: the actions check the DB role with `tieneRolPermitidoEnTx` and an Administrador-only group in `tenant/http/shared.ts` (reuse `ROLES_GESTION_USUARIOS` or add `ROLES_GESTION_SUCURSALES = ["Administrador"]`), deny-by-default, `TEN_OPS_NO_AUTORIZADO` otherwise. All DB access in `withTenantTransaction`; thin adapters; no Prisma in `http/`; typed results with stable codes in `tenant/domain/errors.ts` only; no stack/Prisma error to the client.
- S4 Validation: each of the three fields is required free text, `z.string().trim().min(1).max(255)` like Cliente/Proveedor (the columns are `VarChar(255) NOT NULL`); NO phone or address format check (agent decision L3, no format is documented). Unknown extra input keys are rejected (strict schema, like the siblings).
- S5 Duplicate name rule (agent decision L3): trimmed, case-insensitive, per empresa, counting INACTIVE branches too. Checked inside the transaction (friendly error) AND enforced by the unique index of S2 (a concurrent double create is caught: map the unique violation to the same typed error, never leak a Prisma error). New stable code `TEN_SUCURSAL_NOMBRE_DUPLICADO` (catalog + message; the message says that inactive branches count, since the admin sees only active ones).
- S6 Create: `crearSucursal(nombre, direccion, telefono)` → new row `activa = true`, `version = 1`, `empresaId` from the session (never from input); returns the new branch. Exactly ONE audit row: `ACCION_AUDITORIA.CREAR`, `entidad: "Sucursal"`, `idEntidad` = new id, `sucursalId: null` (company-wide event), after-values in the details. A refused call writes none.
- S7 Edit: `editarSucursal(sucursalId, nombre, direccion, telefono, versionEsperada)`. The target must be a branch of the session empresa (unknown or other-empresa id → `TEN_SUCURSAL_NO_VALIDA`, same answer for both, no oracle). Optimistic lock: verified `UPDATE ... WHERE id AND empresaId AND version` + `version + 1` (stale → the existing `TEN_CONCURRENCIA_CONFLICTO`, nothing changed). Sending the values the branch already has is an idempotent no-op: success, no write, no version bump, NO audit. Duplicate name against ANOTHER branch → S5 error (renaming a branch to its own current name, case changes included, is allowed). Exactly ONE audit row on a real change: `ACCION_AUDITORIA.ACTUALIZAR`, `entidad: "Sucursal"`, before/after of the changed fields, `sucursalId: null`.
- S8 Read side: the Sucursales list returned to the screen (existing admin-only use case `listarSucursalesDeEmpresa`) also carries `direccion`, `telefono` and `version` per branch (needed by the edit dialog). It stays active-only in this slice; the hardcoded "Activa" badge remains. A newly created branch appears everywhere branches are listed (switch, move dialog, tab) with no further change.
- S9 UI (Administrador only, same server gate): on the Sucursales tab a **"Nueva sucursal"** button above the table (dialog with the 3 fields, explicit confirmation, buttons disabled while pending, definitive state shown only after the server confirms, typed error messages from the catalog incl. the duplicate message) and an **"Editar"** row action (same dialog prefilled; sends the row's `version`; a conflict reloads the list and never retries). The table shows Nombre, Dirección, Teléfono, Estado. Spanish copy like the neighbours.
- S10 Tests: domain/use-case unit (validation, duplicate incl. inactive and case/space variants, no-op, version conflict, audit once, no audit on refusal); RLS integration as `systemfact_app` (extend the pattern of `usuario-rls-roles.integration.test.ts`): Operador INSERT/UPDATE refused, Administrador INSERT/UPDATE ok, cross-empresa INSERT/UPDATE refused, DELETE refused for Administrador AND Operador, bootstrap INSERT ok, SELECT behaviour unchanged (an Operador still reads the empresa's branches), the unique index refuses a duplicate under the app role and a case/space variant; use-case integration through `withTenantTransaction`: create, edit, stale version, no-op without audit/version bump, parallel double create of the same name (exactly one succeeds), cross-empresa edit refused. RTL for button, dialogs, empty/error states, duplicate message, conflict. e2e: the Administrador creates a branch through the UI and sees it in the table, then edits it; Operador/Despachador cannot reach it; it must not skip (`app/e2e/assert-no-skips.mjs`) and must not leave a state that breaks the other specs (some assume ONE branch: deactivate or avoid leaving extra active branches, like the slice A e2e does).
- S11 Rollout (owner action, explicit): the migration is additive and backward compatible with the production code (v0.32.0 never writes `SUCURSAL`), so the order is: owner applies the migration with `app/tools/scripts/supabase-prod-migrate.ps1`, the agent verifies it via Supabase MCP (policies, column, index, `_prisma_migrations`), and ONLY THEN the code is merged and deployed (the new Prisma client selects `version`; deploying first would break branch reads). Production deploy only with the owner's explicit approval.
- S12 Version bump 0.33.0 (feat → MINOR) in `app/package.json` + `.release-please-manifest.json` + `app/CHANGELOG.md` (UTF-8 without BOM) in the final patch commit; native review of the migration slice (risk + resilience) before the push.
